# Competitive and complementary tools

Checked against reachable primary sources on **2026-11-03**. “Documented” below means a project's README/official docs say it does something, not that we installed or independently validated it. An undocumented feature is **unknown**, not “absent.” Product positioning and proposed audience are assumptions unless explicitly labelled verified. Repository-specific InfraJournal claims refer to `packages/core/src`, `packages/documentation/src`, `packages/cli/src/index.ts`, `apps/web/src` and `README.md` in this checkout. The original research snapshot predates the `infrajournal@0.1.1` npm publication; package availability does not change the documented feature comparison.

## Meaningful overlap and limits

1. **[compose-viz](https://github.com/compose-viz/compose-viz)** reads Compose and produces multiple graph formats with port/legend controls. This overlaps the _visual explanation_ of Compose services. It documents Graphviz as prerequisite. InfraJournal instead links selected proxy declarations and optional ADRs to a typed snapshot and text docs; **do not** say compose-viz cannot produce other outputs or has no drift facility without checking its implementation.
2. **[docker-compose-viz](https://github.com/pmsipilot/docker-compose-viz)** maps dependencies, ports, volumes and networks, documents `--override` and DOT/image/display options. It already covers Compose structures InfraJournal does not, including an override-related workflow; do not position InfraJournal as having broader Compose support. Its README describes a visualization tool, not a schema-versioned Markdown/JSON baseline workflow.
3. **[docker-compose-viz-mermaid](https://github.com/derlin/docker-compose-viz-mermaid)** produces Mermaid from Compose for use in Markdown and images. Its own roadmap lists network and `extends` support as outstanding; this is **a statement about its published roadmap, not a tested exclusion**. InfraJournal's output emphasizes a reusable inventory and cross-file proxy relations instead of Mermaid source.
4. **[Dockumentor](https://github.com/gni/dockumentor)** is the clearest direct documentation alternative: CLI-generated README, Mermaid and Jinja2 customization, with append markers preserving surrounding author text. InfraJournal's guarded Markdown writes are **not unique** in principle; its distinctive emphasis is versioned normalized inventory and file-baseline drift across the documented Compose/proxy subsets. Dockumentor's repository has no displayed license or `LICENSE` at the checked path: do not claim it is open source under a particular license without verification.
5. **[Compoviz](https://github.com/adavesik/compoviz)** documents browser-only operation, multi-file Compose processing, an editor, YAML export and up-to-three-project comparison for conflicts. It is a meaningful counterexample to “only tool with a UI,” “no one supports multi-file,” and “only local Compose visualizer.” Its comparison is cross-project visual/collision analysis, not InfraJournal's saved-snapshot comparison. Its performance and “spec-compliant” claims are upstream self-descriptions, **not independently verified benchmarks or compliance results**. Its README mentions optional Vercel Analytics in local setup; avoid implying all alternatives send data or are necessarily hosted.
6. **[DockGraph](https://github.com/dockgraph/dockgraph)** provides an interactive UI, optional Compose parsing, Docker event-driven updates, metrics and logs. InfraJournal is deliberately not a substitute for running-system observation. The documented Docker socket requirement creates a different trust boundary (the project itself warns a read-only socket mount is not an API-level permission restriction). Its [BSL-1.1 license](https://github.com/dockgraph/dockgraph/blob/main/LICENSE) means it should be described as _source available_, not unqualified open source.
7. **[InfraMap](https://github.com/cycloidio/inframap)** maps HCL and Terraform state to provider-aware DOT; useful for cloud IaC, not an alternative parser for a Compose-plus-proxy stack. Its README explicitly notes state-version and backend limitations. **Complementary** if a team also uses Terraform.
8. **[D2](https://github.com/d2lang/d2)** is a local diagram language and exporter, **not an automatic Compose parser by itself**; could render data exported by a future InfraJournal adapter. Its current README lists bundled Dagro/elk-go/TALA and MPL-2.0. **Complementary** to fact extraction, not a replacement for it.
9. **[MkDocs](https://www.mkdocs.org/)** builds Markdown into a static site and offers local preview; it does not promise to derive services, domains or drift from files. **Complementary** publishing destination for generated Markdown.
10. **[OpenTofu `plan`](https://opentofu.org/docs/cli/commands/plan/)** compares configuration, prior state and remote objects by default, proposes actions and supports a detailed exit code. InfraJournal `check` compares two _parsed file snapshots_, not infrastructure state. **Complementary** operational/IaC verification, and a reminder not to label InfraJournal's output “actual deployed drift.”

Also relevant: [Diagrams](https://github.com/mingrammer/diagrams) lets authors code cloud diagrams in Python and requires Graphviz; [Docker Compose `config`](https://docs.docker.com/reference/cli/docker/compose/config/) merges Compose files and resolves variables into the model Docker would use. Both are useful reference workflows; neither should be misrepresented as InfraJournal's own capabilities. An additional direct 2026 project, [docker-compose-to-mermaid](https://github.com/TamirTapiro/docker-compose-to-mermaid), advertises offline Compose diagram generation, inferred service relationships, JSON export and CI integration; **README claims are not independent proof that all planned features are implemented** (its own product doc includes MVP/roadmap language).

## Defensible positioning; assumptions clearly marked

**Verified in this repository:** InfraJournal implements a file-only, local-first CLI spanning supported Compose, Nginx and Caddy declarations, an evidence-bearing canonical snapshot/graph, generated Markdown, semantic baseline diff, and a localhost dashboard. Its scanner does not call Docker, a cloud API or an AI service, and no telemetry integration is declared in the checked-in implementation (`packages/core/src/scan/scan.ts`, `packages/core/src/serialization/snapshot.ts`, `packages/documentation/src/`, `packages/cli/src/index.ts`). The generated timestamp can vary; “deterministic” should refer to normalized content and `contentHash`, **not byte-identical whole snapshot files**. The scanner is read-only; `generate`, `init`, `scan --output` and build are not. Privacy is bounded by the machine and potential output exposure, not a promise of secret-free artifacts.

**Assumptions / interpretations:** that this particular bundle in one small CLI solves a substantial unmet need, that users prefer it to a specialist-tool chain, and that the workflow is _smaller_, _easier_, or _more trustworthy_ than alternatives. No package-size, security, user-experience, deployment or market comparison was measured. Claims such as “first,” “only,” “best,” “fully spec-compliant,” “guarantees no secrets,” “documents actual infrastructure,” “always up to date,” or “all competitors require cloud/Docker” are **not supported**. More accurate: “A published pre-1.0 local CLI that documents its supported configuration subset and detects changes between documentation snapshots without contacting a Docker daemon or cloud service during scanning.”

## Verification notes and open questions

- Reachability and described features above were checked from the linked primary sources as of the date at top; future upstream revisions can invalidate feature or license summaries. No competitive tool was executed; README descriptions can differ from production behavior.
- Dockumentor's license is unresolved on its checked repository; do not list it as license-verified open source. DockGraph is BSL-1.1, not an OSI-license claim. Verify other licenses at the upstream license file before redistribution/integration.
- Open: which integrations (Markdown-to-MkDocs, D2 export, Compose pre-processing) are valuable without weakening the no-daemon/no-secret-content boundary?
- Open: whether to add an explicit distinction in all marketing between _documentation configuration drift_ and runtime drift, and whether to note that several other local/offline Compose visualizers already exist.
