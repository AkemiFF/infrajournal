# InfraJournal research and design rationale

Research checked 2026-11-03. **Verified** means the cited repository file, official documentation, or upstream repository describes the claim; it does not mean we independently executed either tool. **Assumption** means a proposed audience, motivation, or interpretation not backed by user research. There are no adoption, speed, or market-size estimates here. See [competitive analysis](competitive-analysis.md) for per-project comparisons.

## Problem and intended audience

**Verified in this checkout:** Compose declares services, networks and volumes, while proxy files declare routes and hosts; InfraJournal combines selected facts from those inputs into a schema-validated snapshot, graph, Markdown, baseline comparison and local dashboard (`packages/core/src/scan/scan.ts`, `packages/core/src/model/schema.ts`, `packages/documentation/src/markdown/generate.ts`, `packages/documentation/src/drift/compare.ts`, `packages/cli/src/index.ts`). The three checked-in examples span Compose-only, Caddy plus Compose, and Nginx plus Compose with optional decision records (`examples/`). The [Compose Specification](https://github.com/compose-spec/compose-spec/blob/main/spec.md) itself distinguishes services, networks, volumes, configs and secrets, and specifies more than this scanner supports.

**Assumption / product hypothesis:** maintainers of small Compose-based stacks, platform engineers, self-hosters and reviewers need a reviewable answer to “what services are declared, what is exposed or routed, what stores data, which decisions explain it, and what changed since the last documented snapshot?” Facts scattered across files and separately maintained diagrams may become inconsistent. There is no user study here establishing how often this happens, how long onboarding takes, or which segment values it most.

InfraJournal's **configuration drift** is the difference between a saved _documentation snapshot of parsed files_ and a fresh scan. It is **not** runtime drift between deployed infrastructure and desired state. The latter is addressed by tools such as [OpenTofu `plan`](https://opentofu.org/docs/cli/commands/plan/), which reads remote object state by default (`packages/documentation/src/drift/compare.ts`).

## Parser design: what is and is not inferred

**Verified:** discovery is glob-based, deterministically sorts results, restricts recognized filenames and Nginx `*.conf`, limits size/depth/count, and skips symlinks resolving outside the root (`packages/core/src/discovery/discover.ts`, `config/schema.ts`). Compose uses `yaml.parseDocument` with unique keys and line positions and limits YAML aliases in `toJS`; it extracts selected services, ports, mounts, networks, dependencies, image/build references, healthcheck, restart, environment _key names_, `env_file` path references and label keys (`packages/core/src/parsers/compose.ts`). In particular, it does not interpret variable expansions or merge Compose files, `include`, `extends` or profiles. A separately discovered Compose file can be scanned, but that is **not** equivalent to implementing Compose merge semantics. Unknown properties can be ignored; do not promise a warning for every unsupported directive.

Nginx and Caddy have custom tokenizers/parsers for their documented syntax (`packages/core/src/parsers/nginx.ts`, `caddy.ts`). Nginx recognizes server names, locations, upstreams, literal proxy targets and TLS declaration; it does not evaluate includes, variables, maps, conditionals or regex matching. Caddy recognizes site addresses, reverse proxies and basic path handling; it does not resolve imports, plugins, placeholders or Unix sockets. Matching literal proxy targets may link to Compose services; environment **key-name** classification may infer dependencies, explicitly marked inferred rather than treated as runtime evidence (`packages/core/src/scan/scan.ts`, `graph/build.ts`). Snapshots are canonicalized and content-hashed; the recorded generation time is metadata rather than an invariant output byte (`packages/core/src/serialization/snapshot.ts`).

## Security boundaries and deliberate MVP omissions

**Verified design constraints:** source scanning does not run Docker, load `.env`/`env_file` values, read bind-mounted host files or follow proxy includes; configured decision YAML is a separate, explicitly selected input and may contain sensitive author-written text (`packages/core/src/discovery/`, `parsers/`, `decisions/load-decisions.ts`; `SECURITY.md`). Files and directories have bounds; output generated from declarations can still reveal internal names and topology. The CLI uses a Node HTTP server bound to `127.0.0.1` for the dashboard (`packages/cli/src/index.ts`). The scanner itself is read-only; **`generate`, `init`, `scan --output` and build steps can write files** (`packages/cli/src/index.ts`). Redaction is best-effort, not a secrecy guarantee (`packages/core/src/utils/redact.ts`). Do not claim that a local UI is authenticated or safe to expose through a public proxy.

**Verified exclusions:** no Docker daemon, runtime state, DNS/firewall/cloud inspection, certificate validity checks, backup verification, hosted service, telemetry, AI dependency, complete Compose-spec implementation, multi-file resolution, or evaluated proxy configuration (`README.md`, `docs/limitations.md`, relevant parsers and CLI). **Design interpretation / assumption:** these are deferred to keep file-only operation, predictable analysis, a small attack surface and clear uncertainty boundaries; a later opt-in runtime integration would be a different security decision. The documentation is evidence about supported declarations, not an audit or an exact simulation of deployment.

## Open research questions (not established facts)

- Which teams want configuration-only drift versus runtime reconciliation, and how should they present both in review?
- Which unsupported Compose/Nginx/Caddy constructs occur most often in target stacks? Collect anonymized, voluntarily contributed fixtures rather than claim coverage without evidence.
- Are users willing to maintain ADR YAML and backup-policy annotations, and does this improve onboarding? No impact study was performed.
- Verify bundled/transitive dependency license notices and obtain an independent security review before stronger release or privacy guarantees.
